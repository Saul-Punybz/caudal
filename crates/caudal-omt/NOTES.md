# caudal-omt notes

## Feed: how raw frames reach ffmpeg (23 Sep 2026)

The ingest path decodes VMX in Rust and needs an H.264/AAC stream. x264 and
AAC stay in ffmpeg, run as an external process (never linked), so raw video
and float PCM have to cross a pipe **with their timestamps**. Three ways were
tried with real ffmpeg on this Mac (Apple M4, 10 cores):

```
ffmpeg version 9.0.1 Copyright (c) 2000-2026 the FFmpeg developers   (/opt/homebrew/bin/ffmpeg)
libavformat 63.1.101 (Lavf63.1.101 in the muxer's tags)
```

### 1. Matroska `V_UNCOMPRESSED` + `A_PCM/FLOAT/IEEE` — chosen

ffmpeg's own Matroska muxer writes raw video as `V_UNCOMPRESSED` with the
pixel format as a FourCC in `Video/ColourSpace` (element `0x2EB524`), and
float PCM as `A_PCM/FLOAT/IEEE` + `BitDepth 32`. Round trip through a pipe,
for each layout:

```sh
ffmpeg -f lavfi -i testsrc2=size=320x180:rate=30 -f lavfi -i sine=f=440:sample_rate=48000 -t 1 \
  -c:v rawvideo -pix_fmt $pf -c:a pcm_f32le -f matroska mkv_$pf.mkv
cat mkv_$pf.mkv | ffmpeg -f matroska -i pipe:0 -f null -
ffprobe -show_entries stream=codec_name,codec_tag_string,pix_fmt,sample_fmt mkv_$pf.mkv
```

| `-pix_fmt` | ColourSpace | demuxed as | pipe decode |
|---|---|---|---|
| `uyvy422` | `UYVY` | rawvideo `uyvy422` | clean |
| `nv12` | `NV12` | rawvideo `nv12` | clean |
| `yuv420p` | `I420` | rawvideo `yuv420p` | clean |
| `p216le` (VMX 10-bit) | — | muxer refuses: "Raw RGB is not supported Natively in Matroska" | — |

Audio came back as `pcm_f32le` / `flt` every time. The header bytes of
`mkv_nv12.mkv` show exactly what `MkvWriter::with_tracks` now writes
(`86 8e "V_UNCOMPRESSED"`, `E0 { B0 width, BA height, 2EB524 "NV12" }`,
`86 90 "A_PCM/FLOAT/IEEE"`, `E1 { 9F channels, B5 rate, 6264 32 }`).

Then our own writer, live, end to end: `tests/feed.rs` feeds a UYVY pattern
and a planar stereo tone through `MkvWriter` (TimecodeScale 1 µs, unknown-size
Segment and Clusters) into `ffmpeg -probesize 32 -analyzeduration 0 -f
matroska -i pipe:0` and gets H.264 + AAC back. Passing.

Why it wins: exact per-frame timestamps (1 µs ticks; 90 kHz → µs → 90 kHz
round-trips exactly), one pipe, header fully describes every stream (no
probing delay), and Caudal already had a live Matroska writer for Opus
(`caudal-transcode/src/mkv.rs`), now extended rather than duplicated.

### 2. NUT (rawvideo + pcm_f32le) — works, not chosen

Same round trip with `-f nut`: `uyvy422`, `nv12`, `yuv420p` all come back
correctly (tags `UYVY`, `NV12`, `I420`, audio `PFD `), with exact rational
time bases (`1/61440` video here, `1/48000` audio). But `p216le` came back
as **`rgb555le`** — NUT's FourCC table maps it wrongly, silently. And a NUT
writer is more code than the EBML we already have (CRC-32 per packet,
VLC-coded headers, frame codes, syncpoints with back pointers). Kept as the
fallback if Matroska ever regresses.

### 3. Two pipes (`-f rawvideo -i pipe:0` + `-f f32le -i pipe:3`) — rejected

The raw demuxers carry no timestamps at all; ffmpeg numbers the frames:

```sh
ffprobe -f rawvideo -video_size 320x180 -pixel_format uyvy422 -framerate 30 \
  -show_entries packet=pts,dts raw.uyvy      # pts=0, 1, 2, ... (frame index)
```

So a dropped frame or a sender clock jump would shift A/V permanently. It
also needs a second fd in the child (`pre_exec` = `unsafe`, or named pipes
to clean up).

### Where 4:2:2 → 4:2:0 happens: ffmpeg (swscale)

VMX decodes natively to UYVY (8-bit 4:2:2) or P216/`Yuv422p`; `vmx-codec`
refuses to decode to 4:2:0 (`Error::Unsupported("decoding to 4:2:0")`), and
browsers need 4:2:0 H.264. The feed sends UYVY as is and ffmpeg converts
(`-vf format=yuv420p`); NV12/I420 input goes straight to x264 (it takes both
natively). Rough CPU, 5 s of 1080p60 (`testsrc2`, 300 frames checked with
`ffprobe -count_frames`) + 48 kHz stereo generated by a separate ffmpeg into
the pipe, measured on the encoding ffmpeg only with `/usr/bin/time -p`, x264
`veryfast zerolatency -bf 0`, 6 Mb/s, AAC 128 kb/s, through the shared lock
(`CARGO_BUILD_JOBS=2`, `nice 10`), load ≈ 2.5:

| input on the pipe | user + sys (s) | ≈ cores at real time |
|---|---|---|
| UYVY (swscale → yuv420p in ffmpeg) | 3.07 + 0.27 = 3.34 | 0.67 |
| NV12 | 2.97 + 0.23 = 3.20 | 0.64 |
| I420 | 2.78 + 0.22 = 3.00 | 0.60 |
| swscale alone, UYVY → yuv420p, no encode | 0.12 + 0.12 (vs 0.02 + 0.10 without the conversion) | ≈ 0.02 |

**Rough, and optimistic:** `testsrc2` is far easier for x264 than camera
video, one run each, a laptop under other load. What it does say: the
conversion is ≈ 0.02–0.07 cores (swscale plus the 33% bigger UYVY pipe
writes), small next to the encode, so a Rust UYVY → NV12 converter is not
worth writing now. The real 1080p60 figure (real content, x86 runner) belongs
in `bench.yml`.

## Timestamps

`time::TimeMap` (see its module docs): OMT 100 ns → 90 kHz video, audio
counted in samples; shared origin = first timestamp of either track; a
timestamp going backwards/repeating or jumping > 1 s re-anchors to "last
output + one interval", adopting the other track's new offset when it fits
so A/V stay together across a sender restart. Audio drift beyond 10 ms is
corrected (gap forward, or drop a chunk when the count runs ahead). Sample
rate capped at 384 kHz; a rate change continues at the same instant, rounded
up (a 30 s fuzz run found a change-and-back that landed one sample early with
round-to-nearest, and a second overlap through i64 saturation with absurd
rates; both fixed, regression tests in `time.rs`).

Fuzz target `omt_time_map` (`fuzz/`): 3.0 M runs in 46 s clean after the
fixes, locally (`cargo +nightly fuzz run --target aarch64-apple-darwin
omt_time_map`).

## Feed: measured behaviour (tests/feed.rs, debug build)

90 frames of 320x180 UYVY at 30 fps + 1600-sample planar stereo chunks,
stamped from an arbitrary OMT clock:

- Out: H.264 320x180 on 90 kHz, AAC 48 kHz; 89 of 90 pictures (the last one
  is still in flight when the input ends), 141 AAC frames (3.0 s).
- Every picture's pts equals an input pts (±1 tick): the stream is on the
  caller's clock.
- First picture at +0 µs, first AAC frame at +12 000 µs relative to their
  inputs, both started at the same instant: A/V offset 12 ms (< 1 frame at
  60 fps). The AAC frames sit on a grid 448 samples (9.3 ms) off the input's
  first sample (encoder priming), and the subscriber, starting at the first
  keyframe, skips the AAC frame before it. Not investigated further.
- ffmpeg is gone (`pgrep -f "service_name=<stream> pipe:1"`) after `finish`
  and after dropping the `Feed`; the stream ends in both cases.

## Not verified

- 1080p60 through `Feed` itself (only the ffmpeg side above was timed), and
  real camera content.
- The pipe at 1080p60 UYVY (≈ 250 MB/s) under load: the queue holds 6
  pictures; a full queue drops pictures (`PushError::Full`), never blocks.
- 10-bit: P216 has no FourCC in Matroska or NUT (above); a 10-bit path would
  need `V_UNCOMPRESSED` with another mapping or a down-conversion to 8-bit.
- Linux ffmpeg builds (CI runners) — same demuxer code, not run here.
